# Autofill Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:subagent-driven-development.

**Goal:** Opt-in, per-site credential storage that fills and submits a login form, with hard attempt limiting so a wrong PIN cannot lock the owner's library card.

**Architecture:** Credentials live in `chrome.storage.local` (plaintext — extensions have no keychain). The background worker owns them and hands one to the content script only when every guard passes. A new `src/content/autofill.js` is the only file permitted to WRITE `.value`; READING `.value` stays banned everywhere.

**Tech Stack:** Unchanged — plain ES modules, no bundler, Vitest + jsdom.

## Global Constraints

- **Reading `.value` is banned in every content-script file, including `autofill.js`.** The extension may inject a credential it holds; it may never learn what the user typed. This is the invariant that survives the reversal.
- Writing `.value` is permitted in `src/content/autofill.js` ONLY.
- Permissions stay exactly `["storage"]` plus the three host permissions. No `tabs`, no `scripting`.
- No network code anywhere. Nothing leaves the machine.
- Autofill is **off by default, per site**. A site with no stored credential never autofills.
- **At most one submission per page load.** After **2 consecutive failures** for a site, autofill disables itself for that site until the credential is re-saved.
- Guards before any fill: `https:`, exact host match, path is that site's login path, and both a password field and a resolvable username field exist.

### Task 1: Credential store, login paths, and the attempt-limit policy

**Files:**
- Create: `src/lib/credentials.js`, `src/lib/autofill-policy.js`
- Modify: `src/sites/{sfpl,goodreads,storygraph}.js` (add `loginPath`), `src/lib/badges.js`
- Test: `test/credentials.test.js`, `test/autofill-policy.test.js`

**Interfaces produced:**
- `loadCredential(siteId) => Promise<{username, secret} | null>` — returns null if either field is missing/blank.
- `saveCredential(siteId, {username, secret}) => Promise<void>` — ALSO resets that site's failure count to 0, because re-saving is the owner asserting the credential is right now.
- `clearCredential(siteId) => Promise<void>`
- `loadFailures(siteId) => Promise<number>` / `saveFailures(siteId, n) => Promise<void>`
- `MAX_CONSECUTIVE_FAILURES = 2`
- `recordOutcome(failures, outcome) => { failures, disabled }` — pure. `outcome` is `'success' | 'failure'`. Success resets to 0.
- `isDisabled(failures) => boolean` — `failures >= MAX_CONSECUTIVE_FAILURES`
- `shouldAutofill({ hasCredential, failures, state, url, adapter }) => { fill: boolean, reason: string }` — pure, no I/O. `reason` is one of `'ok' | 'no-credential' | 'not-login' | 'disabled' | 'insecure' | 'wrong-host' | 'wrong-path'`. Returning a reason string rather than a bare boolean is what makes the guard testable and debuggable.
- `BADGE.AUTOFILL_OFF = { text: '🔒', color: '#B91C1C', title: 'Book Lookup — autofill stopped after repeated failures; re-save your credentials in options' }`
- Adapter `loginPath`: sfpl `'/user/login'`, goodreads `'/user/sign_in'`, storygraph `'/users/sign_in'`.

Storage keys: `cred:<siteId>` and `autofillFailures:<siteId>`. Namespaced so they cannot collide with the existing `mode` / `sites` / `lastQuery` preference keys.

Tests must cover: every `reason` branch of `shouldAutofill`; `recordOutcome` reaching and holding the disabled threshold; success resetting the count; `saveCredential` clearing failures; blank/whitespace credentials treated as absent; a credential for one site never returned for another.

### Task 2: The autofill module and worker wiring

**Files:**
- Create: `src/content/autofill.js`
- Modify: `src/content/runner.js`, `src/background.js`
- Test: `test/autofill.test.js`

**`src/content/autofill.js`** — the only file allowed to write `.value`. It must:
- take `(doc, { username, secret })`, locate the username field via the existing `findUsernameField` and the password field via `findPasswordInput`
- set both values, dispatching `input` and `change` events on each so frameworks notice
- submit via the form's submit button if present, else `form.requestSubmit()`
- return `true` if it filled and submitted, `false` if the fields were not found
- **never read `.value` back to verify.** Verification happens by classifying the next page load, not by inspecting the field.

**Message protocol** (extends the existing `page` message rather than adding a new round trip):
- Worker's reply to `{ type: 'page', site, state }` gains an optional `autofill: { username, secret }`, present only when every guard passes.
- Content sends `{ type: 'autofill-submitted', site }` after submitting, so the worker can judge the next page load.
- Worker keeps a per-tab flag in `chrome.storage.session` (`autofillPending:<tabId>`). On the next `page` report for that tab: still `login` → failure; anything else → success. Either way the flag clears.

The worker validates guards using `sender.url`, NOT a URL supplied by the content script — a compromised page must not be able to talk the worker into handing over a credential.

Content-side one-shot guard: a module-level `submittedThisLoad` flag in `runner.js`. Content scripts re-run per navigation, so it resets naturally.

Tests: jsdom against a realistic login form — fills both fields, dispatches events, submits; returns false when no password field; returns false when no username field; **a source assertion that `autofill.js` contains no `.value` READ**, only writes.
