# Autofill Task 2 report — the autofill module and worker wiring

## What was built

### `src/content/autofill.js` (new)
The only file in the extension permitted to write `.value`. Header comment states
this explicitly and explains why reads stay banned everywhere, including here
(verification happens by classifying the next page load, not by reading the
field back).

`fillAndSubmit(doc, { username, secret })`:
- Locates the password field with `findPasswordInput(doc)` and the username field
  with `findUsernameField(doc)` — both reused as-is, no new field-locating logic.
- Returns `false` immediately, writing nothing, if either is missing.
- Writes `usernameField.value` and `password.value`, dispatching `input` then
  `change` (both `bubbles: true`) on each after writing it.
- Submits via, in order: the form's `[type="submit"]` control (`.click()`), else
  `form.requestSubmit()`, else `form.submit()`. The form is resolved via
  `password.form || usernameField.form` (the native form-association IDL
  property, not `.closest('form')`, so a `form="..."` attribute association also
  works). Returns `false` (no submission attempted) if there is no owning form at
  all — a defensive case beyond the plan's literal wording, covered by its own
  test.
- Never reads `.value`, never logs, never fetches.

### `src/content/runner.js` (modified)
- New static import: `import { fillAndSubmit } from './autofill.js';`
- New module-level `let submittedThisLoad = false;` — resets naturally per
  navigation since content scripts re-run fresh.
- `report()` now checks `reply?.autofill` before the existing `reply?.focus`
  branch: if present and `!submittedThisLoad`, calls `fillAndSubmit`; on `true`
  it sets `submittedThisLoad = true` and fire-and-forgets
  `chrome.runtime.sendMessage({ type: 'autofill-submitted', site: adapter.id })`
  (with a `.catch(() => {})`, matching the project's tolerance for a message the
  caller doesn't need a reply from).
- The existing focus branch is unchanged and still runs for the non-autofill
  case (background.js sends `focus: false` alongside `autofill`, so the two
  branches never both fire for one reply — see below).

### `src/background.js` (modified)
- New imports: `loadCredential, loadFailures, saveFailures` from
  `./lib/credentials.js`; `shouldAutofill, recordOutcome` from
  `./lib/autofill-policy.js`.
- `handlePageReport({site, state}, tabId, url)` gained a third parameter, `url`,
  which the `onMessage` listener now passes as `sender.url` — never anything
  from the message body. This is stated in a doc comment on the function: "A
  compromised page can lie about `state`; it cannot make Chrome lie about
  `sender.url`."
- At the top of `handlePageReport`, before the existing intent/badge logic:
  `resolvePendingAutofill(tabId, site, state)` — checks
  `autofillPending:<tabId>` in `chrome.storage.session`; if set, folds the
  outcome into that site's failure count via `recordOutcome` (`state === 'login'`
  → `'failure'`, anything else → `'success'`), persists via `saveFailures`, and
  clears the marker either way.
- After the existing intent/badge/resume logic (and only if the report didn't
  early-return on `resume`): loads the credential and failure count, calls
  `shouldAutofill({ hasCredential, failures, state, url, adapter })`.
  - `reason === 'disabled'` → overwrites the tab's badge with
    `BADGE.AUTOFILL_OFF` (this only ever fires when `state === 'login'`, by
    `shouldAutofill`'s own guard ordering, so it never clobbers an unrelated
    badge).
  - `fill === true` → reply is `{ focus: false, autofill: { username, secret } }`
    (focus explicitly turned off — we're about to fill and submit the field
    ourselves, not waiting for the owner to use Chrome's own suggestion).
  - otherwise → unchanged `{ focus: decision.action === 'focus' }`.
- New `onMessage` branch for `{ type: 'autofill-submitted', site }`: calls
  `markAutofillPending(tabId)` (sets `autofillPending:<tabId>: true` in
  `chrome.storage.session`), responds `{ ok: true }`/`{ ok: false }`, returns
  `true`, `.catch`-guarded — matching the existing branches' style exactly.
- `chrome.tabs.onRemoved` now also clears `autofillPending:<tabId>`, mirroring
  the existing intent cleanup (not explicitly required by the plan, but the
  same hygiene argument applies: no orphaned session-storage keys for a tab
  that no longer exists).
- Permissions untouched: still exactly `["storage"]` plus the three host
  permissions. No `tabs`, no `scripting` added or needed — everything here uses
  `chrome.storage.session`, `chrome.runtime.onMessage`, and the pre-existing
  `chrome.tabs.update`/`chrome.action.*` calls.

## No-`.value`-read confirmation

`test/autofill.test.js` includes a source-level assertion
(`source: src/content/autofill.js writes .value but never reads it >
contains no .value read — every occurrence is an assignment`) that:
- strips comments and normalizes dot/paren spacing (same technique as
  `security-invariants.test.js`'s `stripComments`/`normalizeSpacing`, kept
  duplicated locally so this test file doesn't depend on another test file's
  internals),
- finds every `.value` occurrence in the stripped source,
- classifies each as a write only if immediately followed by a single `=` not
  part of `==`/`===`,
- asserts the read set is empty, and (positive control) that at least one
  write exists, plus two tests proving the classifier itself would flag a
  genuine read and would not be fooled by `==`/`===` appearing nearby.

All 4 of those tests pass. Manual read of the file confirms the same: the only
two `.value` occurrences are `usernameField.value = username;` and
`password.value = secret;`, both plain assignments.

## `sender.url` confirmation

`handlePageReport` in `src/background.js` takes `url` as its third parameter.
The `onMessage` listener's `'page'` branch calls
`handlePageReport(message, tabId, sender.url)` — `sender.url` comes from
`chrome.runtime.MessageSender`, which Chrome populates itself from the actual
sending frame; `message` (the content script's own payload) is never
consulted for a URL anywhere in this path. `shouldAutofill` receives this
`url` directly. A doc comment on `handlePageReport` states the reasoning
explicitly.

## Deviations from the literal plan text

- `fillAndSubmit` returns `false` if the located fields have no owning `<form>`
  at all (covered by a new test, "returns false when the fields are not inside
  a form at all"). The plan's Task 2 section doesn't mention this case, but
  `findUsernameField`'s formless-widget scope-walk means it's reachable in
  principle; failing closed (no submission attempted) seemed like the only
  choice consistent with the project's "uncertainty resolves to inaction" rule
  already documented in `detect-helpers.js`.
- Used `password.form || usernameField.form` (native IDL property) rather than
  `.closest('form')` to resolve the form to submit, since it also handles the
  (rare) case where a field is associated to a form via a `form="..."`
  attribute despite not being a DOM descendant of it. `.closest('form')` would
  reference the same form in the ordinary nested case that these three sites
  actually use.
- `chrome.tabs.onRemoved` also clears `autofillPending:<tabId>` — not asked
  for explicitly, but mirrors the existing intent-cleanup line right above it
  and avoids an orphaned session-storage key.
- Reply shape when `shouldAutofill` returns `fill: true` explicitly sets
  `focus: false` (rather than omitting the key) — the plan says "Keep existing
  focus behavior for the non-autofill case," which I read as implying the
  autofill case should *not* also request a focus.
