# Autofill cap fix 2: reset requires signedIn, not `results`/`authed` state alone

## Defect (Critical, 2026-08-25 re-review, Finding 2)

`src/background.js`'s `handlePageReport` reset the failure counter to 0 whenever
`state === 'authed' || state === 'results'`. `classify()` in
`src/lib/detect-helpers.js` derives `results` from the URL path alone — SFPL's
`/v2/search` and Goodreads' `/search` serve results pages to logged-out visitors
too — and `runSearch()` opens exactly those URLs as the extension's own core
action. Three ordinary searches after a bad PIN hand-out silently re-armed the
cap the extension exists to enforce, contradicting the spec's "stays off until
the owner re-saves the credential."

## Failing test first (before the fix)

Added to `test/background.test.js`, a `signedIn` param was threaded through the
`pageReport()` test helper, and this regression test was added:

```js
it('REGRESSION: a logged-out results page (signedIn: false) does NOT reset the count', async () => {
  const { sendMessage, local } = await loadBackground({
    localInitial: {
      'cred:sfpl': { username: 'card-1', secret: '1234' },
      'autofillFailures:sfpl': 2,
    },
  });

  await sendMessage(pageReport('results', false), sender());
  expect(local._dump()['autofillFailures:sfpl']).toBe(2);
});
```

## Fix

1. `src/content/runner.js` (`report()`): computes
   `signedIn = matchesAny(document, AUTHED_SELECTORS)` and includes it in the
   `{type:'page', site, state, signedIn}` message. `matchesAny`/`AUTHED_SELECTORS`
   were already exported by `src/lib/detect-helpers.js` — a sign-out control is
   the honest signal, since a logged-out page has no reason to render one. This
   is a boolean classification only; no `.value` read is introduced (confirmed
   by the existing `test/security-invariants.test.js`, which stayed green).

2. `src/background.js` (`handlePageReport`): the reset condition became

   ```js
   if ((state === 'authed' || state === 'results') && signedIn === true) {
     await saveFailures(site, 0);
   }
   ```

   `signedIn` narrows `authed`/`results` from "maybe logged in" to "proven
   logged in" — it does not turn every state into a reset trigger by itself,
   so `challenge`/`unknown` still never reset regardless of `signedIn`,
   matching the spec exactly. A long code comment above the function documents
   why `results` alone was insufficient (naming the logged-out-search-page
   case explicitly) and records this as the second review finding, so nobody
   reintroduces it.

## Tests added (`test/background.test.js`)

- `results` + `signedIn:false` → count preserved (the regression test)
- `results` + `signedIn:true` → count reset, re-armed (updated existing test)
- `authed` + `signedIn:true` → count reset (updated existing test)
- `authed` + `signedIn:false` → count preserved (new)
- `challenge`/`unknown` + `signedIn:true` → count preserved regardless (new)
- End-to-end: wrong credential → two hand-outs reach the cap → three ordinary
  searches landing on logged-out `results` pages → site still disabled, no
  autofill handed out on the next login-page report (new)

## Known, accepted limitation

The content script — running in the page's own origin — is what supplies
`signedIn`, so a page compromised on one of the three allowed origins
(sfpl.bibliocommons.com, www.goodreads.com, app.thestorygraph.com) could claim
`signedIn: true` and reset the cap early. This is accepted: the cap defends
against the extension's OWN repeated submissions locking the library card, not
against a hostile page, and a page already compromised on one of these origins
could do worse than nudge a failure counter.
