# Task 3 report — options UI, invariant split, README

## What was built

1. **Options credential UI** (`src/options/options.html`, `src/options/options.js`, `src/options/options.css`)
   - New "Autofill (opt-in, per site)" section in `options.html`, holding a `#credentials`
     container plus the plain-language storage disclaimer (unencrypted-on-disk, no keychain
     access, readable by anyone with access to the computer or a backup/sync of the profile).
   - Also trimmed the now-inaccurate claim in the existing "Passwords" section ("Chrome
     deliberately blocks extensions from filling password fields without a real click") —
     the design spec explicitly retracts that as a technical claim that was never true; it
     was a policy choice, not a platform limit. Kept the accurate part (default is: no
     password handling, Chrome's own manager + a focused username field) and pointed out
     that this is the *default*, overridden by opting in below.
   - `options.js` renders one block per adapter in `ADAPTERS` (SFPL, Goodreads, StoryGraph):
     a text field (`#cred-username-<id>`), a `type="password"` field (`#cred-secret-<id>`),
     Save/Clear buttons (`#cred-save-<id>` / `#cred-clear-<id>`), a status line
     (`#cred-status-<id>`, "Stored" / "Not stored"), and a disabled-state note
     (`#cred-disabled-<id>`, hidden unless `isDisabled(loadFailures(id))`), which states
     explicitly that saving again re-enables autofill.
   - Save/Clear handlers use the existing `takeTicket()`/`isCurrent()` ticket guard, same
     pattern as `persistSites()` and the mode radios, so a slow save/clear can't overwrite a
     later action's status message.
   - The stored secret is **never** read back into `secretInput.value` — the status text is
     driven by `loadCredential(id) !== null`, never by the credential's contents. Both
     fields are explicitly wiped (`.value = ''`) after every Save/Clear so a just-typed PIN
     doesn't linger in the DOM once storage has its own copy.
   - Also added the 🔒 `AUTOFILL_OFF` badge (already defined in `badges.js` by Task 1) to
     the README's badge table, which had been left out.

2. **Invariant split** (`test/security-invariants.test.js`)
   - Added `WRITE_ALLOWED = ['src/content/autofill.js']` and
     `VALUE_READ = /\.value\b(?!\s*=(?!=))/` — a `.value` occurrence counts as a READ unless
     immediately followed by optional whitespace then a single `=` not itself followed by
     `=` (so `==` / `===` are correctly treated as reads, not assignments).
   - New describe block asserts `autofill.js` contains no `VALUE_READ` match, plus five
     positive controls (see below) proving the rule isn't accidentally inverted.
   - `IN_PAGE_FILES` (total ban) is unchanged; `autofill.js` is not in it.
   - The "audited file list tracks the manifest" test now checks WAR resources against
     `[...IN_PAGE_FILES, ...WRITE_ALLOWED]`, so every WAR entry is guaranteed to be covered
     by exactly one of the two lists, never neither.
   - Fixed the two failing WAR-pinning assertions to the real 8-entry array Task 2
     established in `manifest.json` (verified by reading the file, not guessed):
     `runner.js`, `autofill.js`, `sites/index.js`, `sfpl.js`, `goodreads.js`,
     `storygraph.js`, `query.js`, `detect-helpers.js`.

3. **README** (`README.md`, "Passwords" section replaced)
   - States plainly: autofill is opt-in, per site, off by default; saved credentials live in
     `chrome.storage.local` in plaintext, with the keychain reason spelled out; anyone with
     account/backup/sync access can read them.
   - States reading a field value is banned everywhere without exception, including in
     `autofill.js`, and that this is the property `test/security-invariants.test.js` enforces.
   - States attempt limiting exists specifically so a wrong PIN can't lock the library card
     (one submission per page load, disable after two consecutive failures, re-save to
     re-arm).
   - Kept the existing honest caveat verbatim in substance: the invariant test is a grep over
     source text, not a sandboxed capability check; it catches accidental regressions, not
     deliberate circumvention (bracket notation, destructuring,
     `getOwnPropertyDescriptor(...).get.call(el)`, the 23-constructs verification anecdote
     — all preserved).

4. **`test/options.test.js`** — extended, not rewritten
   - Upgraded the shared `makeFakeStorageLocal` fake to correctly emulate real
     `chrome.storage.local.get`'s three call shapes (string key, array of keys, object of
     defaults) instead of only the object form the old prefs-only tests needed, and added a
     `remove()` implementation — `clearCredential` calls `chrome.storage.local.remove`,
     which the old fake didn't have at all. This was necessary for correctness once
     `options.js` also drives `credentials.js` through the same fake; it does not change
     behavior for the three pre-existing tests (confirmed — see verification below).
   - New tests (10 total, all in the new describe blocks):
     - initial render: "Not stored" + empty fields for every site with nothing saved;
       "Stored" for a site with a saved credential, **secret and username fields still
       empty**; disabled note shown only for the one site over the failure cap.
     - saving: stores `{username, secret}` under `cred:<id>` (observed via
       `storageLocal.set.mock.calls`, the same style the existing site-checkbox tests use
       rather than mocking the module), clears both fields, flips status to "Stored"; a
       second test confirms saving a credential for a disabled site clears
       `autofillFailures:<id>` to 0 and un-hides the disabled note's opposite (hides it).
     - clearing: removes the credential via `storageLocal.remove`, clears fields, flips
       status to "Not stored"; a second test confirms clearing does **not** touch the
       failure count, so a disabled site stays disabled after clearing (matches
       `clearCredential`'s documented contract).

### Positive controls (invariant split), individually confirmed passing:

```
✓ src/content/autofill.js may write .value but never read it > src/content/autofill.js contains no .value read
✓ src/content/autofill.js may write .value but never read it > src/content/autofill.js still has substantial code after stripping
✓ positive controls: the read/write split is real, not inverted > a plain assignment passes the write-allowed rule (it is a write, not a read)
✓ positive controls: the read/write split is real, not inverted > a declaration reading .value fails the write-allowed rule
✓ positive controls: the read/write split is real, not inverted > a strict-equality comparison reading .value fails the write-allowed rule
✓ positive controls: the read/write split is real, not inverted > a loose-equality comparison reading .value fails the write-allowed rule
✓ positive controls: the read/write split is real, not inverted > passing .value to a function call fails the write-allowed rule
```

`x.value = 1` passes the write-allowed rule (no read detected); `const v = x.value`,
`if (x.value === 'a') {}`, `if (x.value == 1) {}`, and `foo(x.value)` all fail it (a read is
correctly detected in each). The loose-equality (`==`) control was added beyond the task's
literal ask (which named `===`) because the same off-by-one risk applies to both operators.

Re-ran `test/options.test.js` before and after upgrading the shared storage fake to confirm
the three pre-existing tests were unaffected by the fake's more faithful `get()` shape and
the new `remove()` method — same 3/3 pass, same assertions, before adding any new test code.

## Deviations from the literal brief

- Edited the existing "Passwords" section's first paragraph in `options.html` (not just
  added a new section) to remove the now-retracted "Chrome blocks extensions from filling
  password fields" claim and to note it describes the *default*, not an absolute. The task
  description for the options UI didn't explicitly ask for this edit, but leaving it as
  written would have had the options page flatly contradict itself one section down (a
  claim of "never sees or stores your passwords" directly above a working credential-save
  form). This mirrors exactly the correction the design spec already made to the README's
  older wording, applied to the sibling copy in `options.html`.
- Added the 🔒 `AUTOFILL_OFF` badge row to README's badge table. Task 1 defined the badge
  but no task's brief mentioned documenting it; leaving it undocumented alongside the other
  three badges seemed like an omission rather than an intentional gap, given Task 3 is the
  one explicitly charged with correcting the README.
- Upgraded `makeFakeStorageLocal` in `test/options.test.js` (get() shape-awareness, added
  remove()) rather than introducing a second fake, since `options.js`'s `init()` now
  exercises `credentials.js` (and thus these code paths) on every test in the file, not only
  the new ones.

## Uncertain / worth a second look

- The disabled-note copy ("Autofill is currently disabled for this site after repeated
  failed attempts. Saving a credential again re-enables it.") is my wording — the brief
  specified the two facts it must convey (disabled + re-save re-enables) but not exact
  phrasing.
- I chose to wipe both the username and secret fields after every Save/Clear, not only the
  secret field. The brief's hard requirement is only "never render a stored secret back into
  the form"; clearing the username too is a UX/defense-in-depth choice on my part (no
  plaintext PIN sitting in a DOM input any longer than needed), not something the brief
  demanded. Easy to revert if the owner would rather the username field stayed populated
  for a quick re-save.
